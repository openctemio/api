# RFC-011 Phase 2 — Validation executor + confirm-or-downgrade loop

**Status:** Proposed
**Extends:** [RFC-011 — Validation engine: dispatch](RFC-011-validation-engine-dispatch.md) (Phase 1, safe-check, shipped) — follow-ups #1 (agent executor) and #2 (`nuclei` re-check)
**Related:** [RFC-012 real BAS execution](RFC-012-real-bas-execution.md), [RFC-017 CTEM prioritization surfacing](RFC-017-ctem-prioritization-surfacing.md) (P5 validation-gated closure), [`architecture/validation-engine.md`](../architecture/validation-engine.md)

## Problem

Phase 1 made Validation *executable* but only at the **lowest rung of the
rigor ladder**: `safe-check` proves an exposure is still *reachable* (TCP/TLS/HTTP,
technique `T1046`) — never that it is still *exploitable*. Measured against the
[ctem.org Validation stage](https://ctem.org/docs/stages/ctem-validation) the
gap is concrete:

- The rigor ladder's **controlled non-destructive proof** rung — "re-run the
  finding's own detection to confirm the condition is real / still present" — is
  declared (`KindNuclei` is a selector constant) but **unbuilt**. Validation
  stops at "reachable."
- Because nothing produces an *exploitability* verdict, the framework's
  **confirm-or-downgrade** outcome cannot fire. The published CTEM benchmark of
  **30–40 % of prioritized exposures downgraded after validation** is
  unrealized, and the Program-Health board (ui #393) renders `downgrade %` as
  **"not measured"** — an honest but avoidable blank.
- The proof-of-fix loop (`fix_applied` → auto re-check, `SetAutoValidator`)
  re-checks with `safe-check`, so a "fixed" claim is confirmed only to the depth
  of "port still open," not "vulnerability actually gone."

This RFC delivers the **middle rung** — automated, non-destructive,
template-driven re-verification — and closes the loop by turning its verdict
into a finding-state transition that either **confirms** (keep open, stamp
proof) or **downgrades** (validated-fixed / de-prioritized, with evidence).

## Goal

When a finding is validated (on-demand, or auto on `fix_applied`), re-run the
**finding's own detection signature** against its asset on an agent,
non-destructively, and move the finding on the result:

- **still detected** → confirm: attach reproduction evidence, hold priority (and
  raise validation confidence).
- **no longer detected** → downgrade: transition to a validated-fixed state with
  evidence, feed the `downgrade %` outcome metric, and (per RFC-017 P5) allow
  validation-gated closure.

Reuse everything Phase 1 already wired: the `validate` command transport, the
completion hook, and the evidence-ingest + redaction + status-reconciliation +
coverage-SLO pipeline. This is **not a new engine** — it is a new executor kind
plus a verdict→state rule.

## Non-goals (this phase)

- **Detect / Respond control-effectiveness** (does the SIEM alert? can the team
  respond?) — needs a SIEM/telemetry seam; deferred to Phase 3. This phase
  measures **Prevent** ("does the exposure condition still exist").
- **Adversary emulation / purple-team** (rigor rung 5) — remains the manual
  pentest module; out of scope for automation.
- **Exploit simulation with a live payload** — RFC-012's lane. This phase runs
  **detection templates only**, never weaponized payloads.

## Design

### 1. `nuclei` executor kind (agent-side — the missing rung)

- The finding already carries the detection signature that first raised it — the
  scanner's rule/template identifier (nuclei template ID, or the CVE the
  template maps to). The `validate` command payload for `KindNuclei` carries
  `{template_id | cve_id, target, timeout}`.
- The agent (`Dockerfile.nuclei` already exists for scanning) runs the **single
  template** against the target: `nuclei -id <id>` / `-t <template>` — reusing
  the SSRF-guarded target validation from `safe-check`. Result is a boolean
  match + sanitized evidence (matched-at, matcher name, response excerpt).
- **Component split** (per RFC-011 follow-up #1): the tenant-runner's fixed
  command-type switch lives in `sdk-go/pkg/core`, so this is an **sdk-go release
  + agent bump**, not an api-only change. The api side only needs the selector
  to route `KindNuclei` when the fleet advertises the `validate:nuclei`
  capability (capability-gated exactly like Phase 1, so dispatch never enqueues a
  command no agent can consume — `ErrNoValidationAgent`).

### 2. Safety / rules-of-engagement (non-negotiable)

The ctem.org ladder ties higher rungs to explicit ROE. For automated
template re-verification:

- **Detection templates only.** Restrict to non-destructive nuclei tags; exclude
  `dos`, `fuzz`, `intrusive`, and any template without a safe matcher. Enforced
  agent-side (allowlist by tag) *and* api-side (reject a `KindNuclei` job whose
  template resolves to an excluded tag).
- **Bounded + logged.** Reuse Phase 1's `defaultTimeoutSeconds`; per-run rate
  limit per asset; every run logged with the command ID (already the audit key).
- **Approval posture.** On-demand validate stays `findings:write`. The
  **auto-on-`fix_applied`** path is opt-in per tenant (rides the existing
  `SetAutoValidator` wiring + a `RiskScoring`-style toggle, default **on** for
  safe-check, default **off** for nuclei until a tenant opts in) — mirroring the
  ownership-floor toggle precedent (#464): no silent escalation of active
  behavior.

### 3. Confirm-or-downgrade rule (api-side — closes the loop)

The completion hook (`triggerValidationEvidence`) already maps a command result
into `validation.Evidence` and ingests it under the command's authoritative
tenant. Extend the **status-reconciliation** step with an explicit verdict rule:

| Validation outcome | Finding state before | Transition | Evidence |
|--------------------|----------------------|------------|----------|
| `not_reproducible` (no match) | open / re-opened | → `validated_fixed` (or downgrade one priority band if policy = de-prioritize-not-close) | "exposure condition no longer observable" |
| `not_reproducible` | `fix_applied` (proof-of-fix) | → `resolved` (verified) | proof-of-fix confirmed |
| `reproducible` (match) | any | hold state; stamp "still exploitable"; raise `validation_confidence` | reproduction evidence |
| `reproducible` | `fix_applied` | **re-open** (fix did not work) | regression proof |

- **`validated_fixed` vs downgrade** is a per-tenant policy knob (some programs
  auto-close on a clean re-verify; others require human closure — RFC-017 P5
  "validation-gated closure"). Default: **downgrade + require human close**, the
  conservative choice.
- Every `not_reproducible` transition increments a **downgrade counter** on the
  cycle/tenant so the Program-Health `downgrade %` becomes real (removes the
  "not measured" blank). Schema: a `validation_outcome` enum + `downgraded_at`
  on the finding (migration `000207`), or derive from the evidence table if a
  read-model suffices — decide at build from the evidence schema.

### 4. Where each rung now lives (the ladder, mapped)

| ctem.org rung | OpenCTEM |
|---------------|----------|
| Configuration validation (low risk) | `safe-check` (Phase 1) |
| Reachability testing | `safe-check` `T1046` (Phase 1) |
| **Controlled non-destructive proof** | **`nuclei` re-verify (this RFC)** |
| Exploit simulation (payload, test env) | RFC-012 BAS lane |
| Adversary emulation / purple team | manual pentest module |

## Phasing

- **2a (api, shippable alone):** selector routes `KindNuclei`; template-tag
  safety guard; the confirm-or-downgrade verdict rule + `validation_outcome`
  schema + downgrade counter; the `downgrade %` metric wired end-to-end (against
  a stubbed/manual nuclei result until 2b lands). Unlocks the metric immediately.
- **2b (sdk-go release + agent bump):** the `nuclei` command executor
  (single-template run, tag allowlist, SSRF-guarded target). Gated behind the
  `validate:nuclei` capability so 2a is inert-safe until the fleet advertises it.
- **2c (ui):** "Re-verify" action on finding detail; the confirm/downgrade
  verdict + evidence on the finding timeline; `downgrade %` label on
  Program-Health flips from "not measured" to live.
- **3 (deferred):** Detect/Respond control-effectiveness via a SIEM seam.

## Why this order

2a is the highest-leverage, lowest-risk slice: it closes the loop and lights up
the outcome metric with **no agent-side attack surface**, because the verdict
rule + metric work the moment *any* validation result arrives (including the
existing safe-check). 2b then upgrades the *depth* of that result from
"reachable" to "exploitable" behind a capability gate, so it can never enqueue a
command an agent can't run. This is the same inert-safe, capability-gated,
opt-in-escalation pattern Phase 1 and #464 established — no big-bang, no silent
active-behavior change.

## Open questions

1. **Template resolution** for findings whose original scanner was *not* nuclei
   (Tenable/Trivy/etc.): map by CVE to a nuclei template where one exists; where
   none exists, fall back to `safe-check` and mark the re-verify "reachability
   only" (honest, not silently weaker). Needs a CVE→template resolver.
2. **Downgrade policy default** — auto-close vs downgrade-and-hold. Proposed
   default: downgrade-and-hold (human closes), overridable per tenant.
3. **`validation_outcome` storage** — new finding columns vs derive from the
   evidence read-model. Decide against the real evidence schema at build.
